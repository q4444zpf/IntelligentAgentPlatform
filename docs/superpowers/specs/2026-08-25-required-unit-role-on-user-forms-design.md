# 用户创建与编辑必选单位角色设计

## 背景

当前用户创建和资料编辑接口不要求角色。管理员可以创建一个状态为启用、具有本地登录凭据、但没有任何单位角色的账号。该账号能够建立会话，却没有可访问页面，容易形成不可用账号。

本次改动要求管理员在新建账号和编辑账号时至少选择一个单位角色，并由后端保证该约束不能被绕过。项目角色继续通过独立的“角色管理”流程按项目分配，不进入本次表单。

## 目标

- 新建账号时至少选择一个启用的单位角色。
- 编辑账号时至少保留一个启用的单位角色。
- 用户资料和单位角色在同一个数据库事务中保存。
- API 拒绝空角色列表、项目角色、停用角色和其他单位的角色。
- 单位角色管理入口不能移除用户的最后一个单位角色。
- 角色发生变化时沿用现有授权版本提升和会话撤销机制。
- 只修改名称或邮箱且角色未变化时，不撤销现有会话。

## 非目标

- 不在新建或编辑账号表单中分配项目角色。
- 不改变独立“角色管理”弹窗的项目角色分配能力。
- 不自动推断或默认选择管理员角色。
- 不自动修复数据库中已有的无角色账号。

## 前端设计

### 数据加载

`UserManagementView.vue` 复用身份管理角色 API，加载当前单位的角色目录。新建和编辑弹窗仅展示同时满足以下条件的角色：

- `scope_type === "unit"`
- `status === "active"`

编辑弹窗打开时，同时读取目标用户当前的单位角色。角色数据加载期间，弹窗保存按钮保持加载状态，避免用未完成的空值覆盖现有绑定。

### 表单行为

新建和编辑弹窗都增加“单位角色”多选控件，并显示为必填项。提交时若选择为空：

- 不调用创建、编辑或角色替换 API；
- 保持弹窗打开；
- 显示“请至少选择一个单位角色”。

新建成功后关闭弹窗并刷新用户列表。编辑成功后关闭弹窗并刷新用户列表。后端返回的角色范围、状态或归属错误使用现有错误展示区域呈现。

### API 请求

创建请求增加：

```json
{
  "display_name": "示例用户",
  "email": "user@example.test",
  "initial_password": "generated-password",
  "role_ids": ["unit-role-id"]
}
```

编辑请求增加：

```json
{
  "display_name": "示例用户",
  "email": "user@example.test",
  "role_ids": ["unit-role-id"]
}
```

前端不采用“先保存用户、再替换角色”的两阶段请求，以免第二次请求失败后留下无角色账号。

## 后端设计

### 请求模型

`CreateIdentityUserRequest` 和 `UpdateIdentityUserRequest` 增加 `role_ids` 字段：

- 类型为 `list[str]`；
- 最少 1 项，最多 64 项；
- 服务层按原顺序去重后校验。

该字段是必填字段，不提供空列表默认值。直接调用 API 的客户端同样必须满足角色约束。

### 角色校验

创建或编辑用户前，在当前管理员的 `unit_id` 范围内一次性查询全部 `role_ids`。只有全部角色同时满足以下条件时才继续：

- 角色存在并属于当前单位；
- `scope_type === "unit"`；
- `status === "active"`。

空列表、项目角色和停用角色返回 `422`。请求包含不存在或其他单位的角色时返回安全的 `422`，不区分不存在与跨单位，避免泄露角色信息。

### 原子事务

创建流程在一次事务内完成：

1. 校验用户字段和角色集合；
2. 创建用户与单位成员关系；
3. 创建本地凭据或邀请状态；
4. 写入至少一条 `UnitMembershipRole`；
5. 记录审计事件并提交。

任何步骤失败都回滚用户、凭据、成员关系和角色绑定。

编辑流程在一次事务内完成：

1. 校验用户、资料字段和角色集合；
2. 更新名称与邮箱；
3. 将当前单位角色替换为请求中的角色集合；
4. 仅在角色集合发生变化时提升 `authorization_version` 并撤销现有会话；
5. 记录审计事件并提交。

独立角色管理接口同步维护该不变量：

- `PUT /api/identity/users/{user_id}/roles` 在单位范围拒绝空数组；
- 单个角色移除接口拒绝移除用户的最后一个单位角色；
- 删除自定义单位角色时，如果它是任一绑定用户的最后一个单位角色，则拒绝删除；
- 项目范围仍允许空数组或移除最后一个项目角色，以支持撤销某个项目的全部授权。

## 兼容性

创建和编辑用户请求新增必填字段，属于有意收紧的 API 契约。仓库内所有调用方和测试夹具必须同步传入 `role_ids`。

已有无角色账号不会在迁移中自动获得权限。管理员需要通过编辑账号选择至少一个单位角色；这样不会擅自授予高权限。

## 测试策略

### 前端

- 新建账号未选角色时阻止提交并显示错误。
- 新建账号选择角色时将 `role_ids` 随创建请求一次提交。
- 编辑账号打开时加载当前单位角色。
- 编辑账号清空角色时阻止提交。
- 编辑账号保存时将资料和 `role_ids` 随同一次请求提交。

### 后端

- 创建和编辑请求缺少或传入空 `role_ids` 时返回 `422`。
- 创建用户时原子写入单位角色绑定。
- 项目角色、停用角色、其他单位角色均被拒绝且不产生部分数据。
- 编辑角色集合发生变化时提升授权版本并撤销会话。
- 编辑资料但角色不变时保留会话。
- 单位范围角色替换拒绝空数组，项目范围仍可清空。
- 单个角色移除和自定义角色删除不能使用户失去最后一个单位角色。

### 回归

- 运行身份管理后端聚焦测试。
- 运行用户管理前端聚焦测试。
- 运行完整后端测试回归。
- 运行完整前端测试、类型检查和生产构建。

## 验收标准

- 新建和编辑账号界面均无法在未选择单位角色时保存。
- 通过 API 无法创建或保存零单位角色账号。
- 成功创建的本地账号首次登录后至少拥有一个由所选单位角色授予的页面权限。
- 角色变更后的旧会话失效，角色未变的资料编辑不影响现有会话。
